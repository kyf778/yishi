## 二、今天没干完的：图片识别太慢 ⏳

### 实测数据（都在电脑上跑的公网调用）

| 场景 | 耗时 |
|---|---|
| 纯文字（短） | 4.0 s |
| 纯文字（普通） | 5.4 s |
| 图片 1 块（1080×1400） | 9.4 s |
| 图片 1 块（1440×1400） | 10.2 s |
| **图片 3 块（1440×3200，你实际用的）** | **42 s** / 另一次 14.9 s |
| 图片小图（720×900） | 5.8 s |

### 已经定位到的

| 发现 | 数据 |
|---|---|
| 网络不是主因 | DNS 128ms、TCP 181ms、TLS ~1.3s、GET /models 1.5s |
| NAS 内部很快 | 本机三跳都在 3-4 秒 |
| **瓶颈是视觉 token** | 单块 1080×1400 → `prompt_tokens=2003`；720×900 → 只 `464` |
| 换模型差别不大 | glm-5.3-flash 13.1s / deepseek-v4.1-flash 11.7s / hy3-x 16.6s |
| 3 块一起发 | 14.9s；比 42s 那次好，怀疑**冷启动** |

### 还没验证的假设（明天第一件事）

1. **冷启动**：同一个请求连发 3 次，看第 1 次是否明显慢
   → 脚本已写好：`test_cold_start.py`（第 1 节就是测这个）
2. **图片尺寸是不是过大**：现状 1600 宽 / 1400 高
   → 缩到 1080 甚至 900 会不会又快又准（脚本第 2 节）
3. **max_tokens 是否过大**：现状 1200，实际输出只要 ~90
   → 降到 400/800（脚本第 3 节）

### 明天可能的优化方向

| 方向 | 预期效果 |
|---|---|
| 图片缩到 1080 宽 | token 从 2003 → 约 1340，可能省 2-3 秒 |
| 图片缩到 900 宽 | token 约 900，最省，但可能影响识别 |
| max_tokens 从 1200 → 400 | 减少生成时间 |
| 只用第 1 块（若关键信息在上面） | 少发 2 块 |
| 换 `deepseek-v4.1-flash`（实测 11.7s） | 比 hy3 略快 |

**重要**：优化前要**确认识别准确率不下降** —— 这是课程设计的核心功能。

## 五、踩过的坑（明天别重复）

| 坑 | 结论 |
|---|---|
| **命名混淆** | 插件界面的「WorkBuddy **国内版**」= 内部 provider `buddy` = `www.codebuddy.cn`，productCode 是 **`codebuddy`** 不是 workbuddy |
| **CodeBuddy 强制流式** | 非流式直接 `400 11101`；桥已处理 |
| **`free-queue` 会选到坏车道** | 实测 404，所以 App 里**点名模型** |
| **模型白名单** | bridge 只放行 `-free` 结尾或白名单里的 |
| **PowerShell 引号地狱** | `$(...)` 被 PS 解析、嵌套引号报错 → 复杂命令写成 `.sh` 再 scp |
| **NAS 主机没 node** | 用 `docker run --rm node:22-alpine` 跑脚本 |
| **凭据文件 BOM** | PS 的 `Set-Content -Encoding UTF8` 会加 BOM → 用 `UTF8Encoding($false)` |
| **小米相册不认 adb 点击** | 系统选择器对合成输入有限制，最后一步得你手动点 |
